## test_01：打造你的第一个 Agent

基于 LangChain 1.x 的 `create_agent` 统一接口，构建一个能自主调用工具回答问题的 Agent。

### 本节学到什么

1. **Agent 是什么**
   - Agent =「模型 + 工具」的组合，模型负责理解问题、决策要调哪个工具，工具负责执行具体操作（查天气、算数）。
   - 相比纯 LLM 对话，Agent 能访问外部真实数据，回答不再是"编的"。

2. **LangChain 1.x 新版 API（关键）**
   - `init_chat_model("deepseek:deepseek-v4-flash")`：统一入口，通过 `provider:模型名` 前缀选服务商，无需直接 new 具体模型类。
   - `create_agent(model, tools, system_prompt)`：统一 Agent 构造器，返回的是一个 **LangGraph 编译图**，所以入口对话格式是 `{"messages": [HumanMessage(...)]}`，结果从 `result["messages"][-1].content` 取。
   - `@tool` 装饰器：把普通函数包装成"模型可感知、可调用"的工具，docstring 就是工具的说明。

3. **工具接入真实数据（和风天气）**
   - 用真实 HTTP 调用替代伪代码里的硬编码假数据，体现"工具 = 真实能力注入"。
   - 和风天气 2026 年起**强制使用账号专属 API Host**（形如 `xxx.re.qweatherapi.com`），宿主即认证要素；用旧的公共 `devapi.qweather.com` 会返回 403 Invalid Host。
   - 天气数据请求时可能返回 **gzip 压缩**，`urllib` 不自动解压，需声明 `Accept-Encoding: gzip` 并手工 `gzip.decompress`。

4. **安全工程化（为什么不用 eval）**
   - 伪代码用 `eval(expression)` 算表达式，但 `eval` 能执行任意 Python 代码，是**注入漏洞**。
   - 正确做法：用 `ast` 解析表达式，**白名单**只放行数字和四则运算节点，其余一律拒绝。安全且同样得到计算结果。

5. **Agent 的自主性**
   - 温差问题无需指令：Agent 看到问题后自动决定连续调用两次天气工具，再用拿到的真实温度自己计算差值。
   - 数学问题 Agent 可能直接用 `calculate` 工具，也可能自己心算——取决于模型决策，这正是 Agent 的行为特征。

### 运行方式

```powershell
cd langchain-lab
.\dev.ps1 examples/test_01/agent.py
```

### 关键踩坑记录

| 现象 | 根因 | 解决方案 |
| --- | --- | --- |
| 天气接口 403 Invalid Host | 用了公共 `devapi` 域名，2026 起需专属 API Host | 改用控制台专属 `xxx.re.qweatherapi.com`，Host 只存 `.env` |
| JSON 解析 UnicodeDecodeError 0x8b | 响应是 gzip，未解压 | 声明 Accept-Encoding: gzip 并手工解压 |
| ModuleNotFoundError: langchain_deepseek | `deepseek:` provider 需要额外集成包 | 在 pyproject.toml 增加 `langchain-deepseek` 依赖并重建镜像 |
| eval 安全问题 | `eval` 可被执行任意代码 | 用 `ast` + 白名单安全求值 |

## test_02：Chat Model 的常规用法与高级用法

学习 Chat Model 两种输出模式：`bind_tools` 让模型"可以"调用工具，`with_structured_output` 强制模型按 Schema 输出结构化结果；并手写一遍"拿到 tool_call 后二次注入模型"的完整闭环，理解 Agent 的底层机制。

### 本节学到什么

1. **Chat Model 常规/高级用法**
   - 模型可固定为具体型号，也可做成可配置模型。
   - 了解关键参数类型与用途：`temperature`（采样温度）、`max_tokens` 等。

2. **bind_tools()：工具绑定**
   - 入参描述支持直接传 JSON 字典、JSON Schema 或 Pydantic 模型；Pydantic 有类型校验、IDE 补全、可复用，更易维护，模型遵守率通常也更高。
   - 注意：`bind_tools` 只让模型"可以"发出工具调用请求，不保证调用、不执行工具；收到请求 → 执行 → 回填的循环发生在 Agent 层。

3. **with_structured_output()：强制结构化输出**
   - 模型无法选择不结构化，输出即 Pydantic 实例。
   - 支持嵌套结构（Recipe → Ingredient / CookingStep）。

4. **temperature=0 的适用场景**
   - 结构化提取、工具入参解析属确定性任务，temperature=0 让输出格式最稳定、可复现；创意写作等发散任务则需高温度。

5. **tool_call 的二次注入（手动 Agent 闭环）**
   - `bind_tools` 只拿到模型的"调用请求"（tool_calls），要得到最终答案必须：应用侧执行工具 → 把结果以 `ToolMessage` 回填对话历史 → **再次发送给模型**。
   - 关键点：`ToolMessage` 靠 `tool_call_id` 与模型发出的 `tool_call["id"]` 关联；工具名取自绑定 Pydantic 类的类名，需与 `tool_call["name"]` 一致。
   - 执行工具的方式：`TOOL_REGISTRY[tc["name"]](**tc["args"])`——先按 name 字典查表拿函数对象，再用 `**` 把 args 字典展开成关键字参数调用。
   - 这整套循环正是 `create_agent` 自动做的事，手写一遍即可理解 Agent 的本质，也便于在自己编排的多轮流程中复用。

6. **tool_choice 与 tool_call 的区别**
   - `tool_choice` 是**请求参数**：控制模型本轮是否调用工具（auto / required / 指定某个工具），随请求一起发给模型。
   - `tool_calls` 是**响应产物**：模型实际决定发起的调用列表（含 name / args / id），从模型返回的 AIMessage 上读取。
   - 一句话记忆：tool_choice 管"允不允许调"，tool_calls 是"实际调了什么"。

7. **DeepSeek 思考模式（thinking mode）对参数的影响**
   - 默认开启思考模式，模型会先生成 `reasoning_content` 思维链再作答。
   - 思考模式下 **`tool_choice` 不被接受**（报 400），且 **`temperature` 等采样参数不生效**（设置了也不报错，容易误判）。
   - 机器消费/结构化提取/代码/数学等需确定性的场景，应显式关闭思考：`extra_body={"thinking": {"type": "disabled"}}`，此时 `temperature=0` 才能保证输出稳定、可复现。

### 运行方式

```powershell
cd langchain-lab
.\dev.ps1 examples/test_02/structured_output.py
.\dev.ps1 examples/test_02/bind_tools.py
.\dev.ps1 examples/test_02/tool_call_loop.py
```

### 关键踩坑记录

| 现象 | 根因 | 解决方案 |
| --- | --- | --- |
| with_structured_output 报 400 "Thinking mode does not support this tool_choice" | DeepSeek 思考模式不接受 `tool_choice`，而 with_structured_output 默认以 function_calling 强制 `tool_choice=required` | 关闭思考模式：`extra_body={"thinking": {"type": "disabled"}}` |
| 设了 temperature=0 但行为不具确定性 | DeepSeek 思考模式下 temperature/top_p 等采样参数不生效（设置了也不报错） | 关闭思考模式后 temperature 才真正生效 |

## test_03：工具高级特性

在真实天气 API 上重新实现 runoob 两章笔记（@tool 基础 + 工具高级特性），用真实数据看清"每个特性何时必需"。

### 本节学到什么

1. **为什么笔记枯燥（认知纠偏）**
   - 假数据工具没有真实副作用，只是"Python 函数假装干活"，体会不到工具价值。
   - 真实项目工具**必须有真实 I/O**（外部 API / 数据库 / 日志）——模型负责决策、工具负责真实做事。

2. **args_schema（Pydantic 入参校验）**
   - 用 `Literal` 限定 city 为支持城市白名单，脏参数在进外部 API 前被拦截（ValidationError），不浪费真实调用、避免 4xx。
   - 真实场景：任何调外部 API / 数据库的工具，先校验再放行。

3. **ToolException + handle_tool_error**
   - `ToolException` 表达"业务级错误"，区别于 args_schema 的"类型/格式错误"。
   - `handle_tool_error=True` 后，错误信息作为正常返回值交给 Agent，模型能阅读错误、引导用户或自我修正；False 则向上抛异常。
   - **关键 API 差异（踩坑）**：langchain 1.3.15 的 `@tool()` 装饰器**不接受 `handle_tool_error` 参数**，随笔注释写法会 `TypeError`。正确做法是给工具实例属性赋值：`tool_obj.handle_tool_error = True`（单数）；复数 `handle_tool_errors` 属于 ToolNode/图层面。

4. **return_direct**
   - 查询型工具（天气/汇率/地图）"结果即答案"，设 return_direct=True 后模型不再二次加工，直接作为终答，省 token、降时延。
   - 注意：同一轮若同时触发 return_direct 与其他普通工具，普通工具结果不会被总结。
   - 判断标准：结果是否"本来就是要给用户看的那句话"，是→return_direct。

5. **InjectedToolCallId**
   - 由 LangChain 运行时自动注入当次 `tool_call["id"]`，不在工具 schema 里、模型看不到。
   - 用于审计日志、埋点、把工具结果绑定回对话上下文。
   - 直接 `.invoke(tool_call)` 手动构造 ToolCall 仅为演示注入机制，真实项目由 Agent 自动注入。

### 运行方式

```powershell
cd langchain-lab
.\dev.ps1 examples/test_03/01_args_schema.py
.\dev.ps1 examples/test_03/02_tool_exception.py
.\dev.ps1 examples/test_03/03_return_direct.py
.\dev.ps1 examples/test_03/04_injected_tool_call_id.py
```

### 关键踩坑记录

| 现象 | 根因 | 解决方案 |
| --- | --- | --- |
| `@tool(handle_tool_error=True)` 抛 TypeError | langchain 1.3.15 的 tool() 装饰器不支持该参数 | 创建工具后给实例赋值 `obj.handle_tool_error = True`（单数） |
| 笔记假数据学不到东西 | 工具无真实副作用 | 换真实天气 API，让工具真实调用外部系统 |
| Language 城市参数校验 | —（示范） | args_schema + Literal 白名单，拦截再放行 |
